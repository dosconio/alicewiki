2026-11-21　95-Camera / OV5640 调试记录

环境与边界

	阿波罗 STM32H743 开发板，购买的 OV5640 模块直接插摄像头接口。
	参考实验38摄像头、实验46照相机及 D:\tmp\cam 中的模块资料。
	使用 UniSYM DCMI、DMA、软件 IIC、LTDC、SDRAM、SD/FAT。
	以下区分代码核对、用户板上日志和推测；构建、烧录、硬件测试由用户执行。

一、编译问题先按项目真实类型处理

	DCMI.cpp 使用 SysCtrlBlock_Map 判断中断嵌套时，需要显式包含声明它的 CortexM7.h，
	不能依赖其他外设头文件间接提供定义。
	Reference(mpu_region) = 0 这类写法可能被解析成声明，造成 vexing parse 和构造歧义。
	改为 Reference region{mpu_region} 等具名对象，再赋值；不要靠猜测构造重载解决。

二、初始化成功与视频采集成功是两件事

	ID=0x5640、寄存器写入成功、4077 字节自动对焦固件上传成功，只说明控制链路可用，
	不能据此认定 DVP 极性、像素时钟、输出尺寸、DCMI/DMA 都正确。
	启动时把 SDRAM/LCD、传感器寄存器、固件、连续对焦、SD/FAT 分段计时。
	修改软件 IIC 位延时后，典型日志为：寄存器约180 ms、固件约770 ms、
	连续对焦约1930 ms、SD/FAT约39 ms；连续对焦本身也占据启动时间。

	OV5640_t::DelayBus 原先使用 SysDelay_us(5)，导致控制总线操作明显拖慢。
	参照已有软件 IIC 例程，改为短的 volatile 循环。电源时序、复位和固件轮询的
	毫秒级等待仍保留；不能把所有等待一概替换成空循环，也不能忽视优化等级的影响。

三、先核对共享引脚，避免把另一外设的配置误判为采集故障

	桌面的阿波罗 IO 分配表与原例程一致：
	PC8：SDMMC D0 / DCMI D2；PC9：SDMMC D1 / DCMI D3；
	PC11：SDMMC D3 / DCMI D4。
	摄像头 HREF 使用 PH8，不能混淆 PH7。
	初始化 SD 或保存照片时，必须先停止采集并关闭传感器数据输出，再切换共享引脚。
	恢复摄像头时重新配置 AF13，再打开输出。采集中不访问 FAT、不切换共享引脚。
	板上读回 PC8/PC9/PC11 均为 mode=2、AF=13，且 SD 无活动数据传输，
	这使当时的持续故障不能仅用“SDMMC 与 DCMI 引脚冲突”来解释。
	/PHOTO 是 SD 卡上的照片目录，不是摄像头或图像格式的名称。

四、用寄存器读回确认极性、尺寸与真正的数据流

	最初现象：LINE/VSYNC 计数增加，但 DMA NDTR 始终为48000。
	这证明同步事件能被看到，却不能证明像素已经搬入内存。
	DMAMUX1 请求读回0x4B，即75，与 DCMI 请求一致。

	原例程和模块参考配置均有 OV5640 0x4740=0x21；实际运行一度读回0x20。
	0x20与0x21相差 VSYNC 极性位。配置采集前显式写0x21并读回确认后，
	NDTR 开始下降。这是极性修正有效的板上证据，但当时仍有后续溢出。
	没有定位到是谁把寄存器改成0x20，不能把原因直接归给对焦固件。
	DCMI 保持参考配置：PCLK上升沿、VSPOL=0、HSPOL=0。
	比较不同器件的高低有效描述时，应看时序与寄存器定义，不能仅凭名称翻转极性。

	输出尺寸使用组写入，组设置可能在帧边界生效。曾请求800x480，立即读回仍是1280x720。
	setOutput 增加有界轮询，确认0x3808～0x380B已经变成目标尺寸后再采集。
	SCCB/IIC 的 ACK 只表示通信应答，不等于整组配置已经在图像输出端生效。

五、错误码必须结合发生路径和现场寄存器解释

	0x01 为 DCMI OVR；0x40 为驱动的 DMA 错误位。
	曾多次出现 DCMI error=0x41，而 DMA error=0：DCMI 溢出中止路径中的回调
	附加了0x40，不能据此声称 DMA 硬件发生 TE。
	软件的双缓冲追赶检查、容量检查和帧尾检查也可能设置0x01。
	所以“0x01”不等于已经确认硬件 FIFO 溢出，必须识别设置错误的具体分支。

	使用错误回调保存首个现场，在主循环统一打印，避免在 ISR 中输出串口：
	DCMI CR/SR/RISR/MISR/IER；DMA CR/FCR/NDTR/LISR、PAR/M0AR/M1AR；
	LINE/VSYNC、最小 NDTR、DMAMUX 请求、时钟与已复制字节数。
	错误清理后 RISR/LISR 为0，不表示清理前没有错误。
	已复制字节数也必须在硬件错误路径发布，否则0只能表示尚未发布，不能表示没有搬运。

	曾出现每帧约9818次 DMA FIFO 错误回调。只忽略 FE 回调仍有中断开销。
	核对原例程后，DCMI 启动路径关闭 FE 中断，保留 TE/DME/TC 的检查；
	帧尾同样不把已禁用 FE 中断对应的原始标志无条件当成有效错误。
	这不是允许忽略所有 DMA 错误，也不是修改共用 DMA 驱动的理由。

六、LCD 与采集并发访问内存的隔离实验

	直接把800x480 RGB565整帧 DMA 到 SDRAM 时，半满 FIFO、逐字写入持续失败。
	预览改为满 FIFO、INC4 后曾成功完成一帧，但仍间歇溢出。
	JPEG 暂保留半满 FIFO、单次内存传输；不要把预览配置的效果自动推广到 JPEG。

	首次预览溢出后临时暂停 LCD 扫描，连续采集8帧，再恢复 LCD。
	多轮用户日志均为：LCD开启时失败，关闭时8/8成功，恢复后再失败。
	这强烈支持并发内存访问/仲裁延迟相关，而不是仅靠优化等级或中断优先级解释。
	DCMI/DMA日志中的A0/B0是优先级编码；相同抢占优先级下，子优先级只影响仲裁顺序。
	调中断优先级不能直接修复总线带宽或硬件 FIFO 的服务延迟。

	把采集缓冲从0xC0200000移到0xC0B00000，与LCD缓冲0xC0000000分属不同
	SDRAM内部bank。板上验证仍失败，说明单独分bank不足以解决问题。
	该试验无效必须如实记录，不能写成已经解决争用。

	原例程先接收至内部 SRAM，再复制到屏幕/外部存储；迁移时直接写 SDRAM 是重要差异。
	查阅 Listings/main.map，确认默认 RW/ZI 位于0x24000000的 AXI SRAM，
	且栈、启动堆也在该区域。不能只检查 Objects 目录就声称没有 map。
	随后在 DCMI.cpp 放置两个32字节对齐、各16 KiB的静态缓冲，由链接器分配地址。
	板上曾读到 M0=0x240023C0、M1=0x240063C0；这些是当次链接结果，不应写死。
	启动前清理并失效缓存，消费 DMA 数据前失效对应缓存行；缓冲不与其他对象共享缓存行。
	启动时还检查 SRAM 地址区域，避免被链接到 DMA 无法访问的 DTCM。

	SRAM双缓冲后，用户确认预览有画面且一度没有报错，BMP保存成功。
	之后仍观察到偶发硬件溢出，因此当时不能宣布长时间稳定。
	最初800x480预览按3000字/12000字节一块复制，与原例程的每行400字不同。
	后续将图像快照改为按对齐的整行分块：800x480 RGB565为400字/1600字节，
	JPEG块长对齐原例程的2048字/8192字节。两个静态缓冲的分配容量不变。
	这样缩短一次连续复制和屏蔽中断的时间；不能代替长时间板测的结论。

七、刷新率测量与一次失败的优化

	用 DWT CYCCNT 计时，核心频率实际读回400 MHz；不靠写死的480 MHz换算。
	每约一秒报告一次窗口平均采集耗时、显示耗时和有效显示 FPS，避免每帧打印。
	DWT可以统计屏蔽中断期间的周期；32位差值适用于单次计时间隔不超过一次回卷。
	命令执行、串流切换和错误恢复会重置预览统计窗口，避免混入拍照/对焦等待。

	当时稳定段实测：capture约132 ms、display约112.6 ms、FPS约4.0。
	132+112.6约245 ms，与4 FPS吻合。它是当前串行实现的结果，不是硬件性能上限。
	当前流程为单帧采集、SRAM分块复制、停止采集、CPU复制整帧到LCD、再开始下一帧。
	配置切换时还丢弃第一帧，因此启动和按U之后的首个统计窗口更慢。
	成功路径没有固定200 ms延时；200 ms只用于操作失败后的恢复。

	曾同时展开 SRAM 复制循环，并把显示的逐字节复制改为展开的32位复制。
	用户立即报告预览重新持续溢出，两项性能改动已撤回。
	由于当时同时改变了两处，不能断言具体是哪一处或哪种总线行为导致回归。
	撤回后也曾观察到偶发溢出，说明原实现仍有稳定性余量问题。
	经验：不要同时更改采集中断路径和显示路径；保留已验证版本，一次只验证一个变量。
	更快的CPU循环不一定让实时采集更可靠，应同时观察DMA进度、错误和总线访问延迟。

八、JPEG失败的确定性错误：停止 DMA 本身也会产生 TCIF

	JPEG由 OV5640 内部硬件编码后，通过 DVP 输出压缩字节流。
	DCMI 的 JPEG 模式只接收数据，STM32在此流程中不做 JPEG 编码。
	JPEG长度可变，不能像RGB565那样只靠固定整帧字数判定完成；帧末必须停止并收取尾块。

	曾出现 JPEG error=0x01、state=4、DMA error=0、DMA已停止且中断标志已清理。
	这个现场不能直接认定码流太快或 SD 卡保存失败，必须检查帧尾软件判错逻辑。
	对比原例程发现：它在帧末停 DMA，等待 EN=0，再根据 CT、NDTR 复制当前缓冲尾部。
	RM0433 §15.3.15～15.3.16明确：软件清除 EN 中断传输后，也会置位 TCIF；
	外设到内存方向还涉及 DMA FIFO 向内存排空。这不是“完整数据块又收到了一次”的证明。

	原错误判断使用 (停止后的flags | 停止前的pending_flags) 检查TCIF，
	在CT与已复制块数一致时误认为发生回卷，于是正常收尾也可能被报成OVR。
	最终修正：仅用停止前保存的pending_flags判断这一类积压；
	停止后的TCIF不再作为回卷证据，但仍保留真正的TE/DME错误检查。
	结合CT与已复制完整块数，先收取尚未处理的完整块，再根据NDTR收取尾块；
	继续保留容量上限、缓冲切换和复制追赶检查，不能简单屏蔽OVR来“通过”。
	这次只修改这一项判断，没有继续改时钟、FIFO或复制循环。用户随后确认 JPEG 成功。
	这是本轮最明确的逻辑错误：把停止动作产生的正常状态标志，当成了数据丢失证据。

	预览按键：U缩放/裁剪，D保存JPEG，L对焦，R保存BMP。
	串流按键：U尺寸，D对焦，L效果，R对比度。

	编号递增并跳过已存在的同名文件。JPEG有效范围由FF D8和FF D9界定，排除末字填充。
